# {{ pcsm.full_name }} 1.1.0 ({{ date.v1_1_0 }})

{{ pcsm.full_name }} (PCSM) 1.1.0 adds control over chunk pre-splitting during the initial clone and fixes a finalization deadlock after high availability failover.

[Get started with {{pcsm.short}}](../installation.md){.md-button}

## Release highlights

### Control chunk pre-splitting during the initial clone

When migrating between sharded clusters, you can now skip pre-splitting collections on the target. This is useful when you want the target balancer to manage chunk distribution instead of copying the source cluster's chunk boundaries.

Set `--clone-skip-presplit` on `pcsm start`, set the `PCSM_CLONE_SKIP_PRESPLIT` environment variable, or set `cloneSkipPresplit` in the `/start` request body.

PCSM still shards the target collection using the source shard key. Pre-splitting remains enabled by default. The option is not saved in recovery checkpoints.

For more information about chunk distribution, see [sharding support](../sharding.md#chunk-distribution).

### Resume finalization after high availability failover

If the active PCSM instance becomes unavailable during finalization, a promoted standby instance restores the saved state. You can now reissue `/finalize` on that instance to resume finalization without the request or subsequent `/status` requests hanging.

Finalization does not resume automatically after promotion. PCSM also rejects a second finalization request while finalization is already running in the same instance.

For more information, see [high availability](../high-availability.md).

## Changelog

### Improvements

* [PCSM-382](https://perconadev.atlassian.net/browse/PCSM-382): Added the `--clone-skip-presplit` option to `pcsm start`, the `PCSM_CLONE_SKIP_PRESPLIT` environment variable, and the `cloneSkipPresplit` field in the `/start` request body. You can skip target chunk pre-splitting during the initial clone while retaining the source shard key.

### Bugs fixed

* [PCSM-385](https://perconadev.atlassian.net/browse/PCSM-385): Fixed a deadlock when finalization was requested on a promoted standby instance after recovery. The `/finalize` request could previously hang and block subsequent `/status` requests. You can now reissue `/finalize` to resume interrupted finalization. PCSM also rejects concurrent finalization requests in the same instance.
